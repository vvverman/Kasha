# Kasha Desktop: реализация, сборка и установка

Обновлено: 14 сентября 2026. Требования: [SPEC.md](SPEC.md), общий интерфейс: [design/README.md](design/README.md).

Desktop — один модуль `platforms/desktop` с Gradle-именем `:desktopApp`. macOS, Windows и Linux используют существующие Core, общий Kasha UI и JVM infrastructure. Бизнес-правила, сортировки, AI-контракты и продуктовые экраны не переносятся в shell.

## Порядок работ

По указанию владельца сначала завершается реализация; глубокая приёмка проводится отдельно. Статус «реализовано» не означает «проверено на физическом устройстве» или «готово к выпуску».

| № | Этап | Реализация | Подтверждение |
|---|---|---|---|
| 1 | Стабилизация переноса | Выполнена: исправлены пути и зависимости, CI достигает packaging | Подтверждено предыдущими прогонами |
| 2 | Единый desktop-слой | Реализованы каталоги ОС, bundled executables, запись, воспроизведение, журнал, защищённые секреты, уведомления и single-instance | Есть существующие тесты адаптеров |
| 3 | Windows | MSI с внешними CAB, EXE, встроенные движки и GGUF-шарды; добавлены MSI AppUserModelID, согласованные кодировки MSI/WXL и ожидание завершения install-smoke | Новая упаковка и установка ещё требуют успешного CI |

## Установочные форматы

Готовые пакеты следует брать из успешного запуска соответствующего GitHub Actions workflow. Наличие исходников установщика не означает, что для последнего коммита уже опубликован рабочий пакет.

### Windows x64

`package-windows.ps1` формирует два варианта: самостоятельный Inno Setup EXE и MSI с соседними `kash*.cab`. Для установки через MSI все CAB должны оставаться рядом с MSI; один MSI не содержит модели. EXE включает полезную нагрузку самостоятельно.

Java, Whisper, llama.cpp, FFmpeg и базовые модели включаются в пакет. Qwen разбивается штатным `llama-gguf-split` на части; это не уменьшенная и не переквантованная модель. AppUserModelID ярлыка и notifier одинаковый: `ru.vrmn.kasha`.

Данные: `%APPDATA%\Kasha`. Секреты внешнего AI: DPAPI CurrentUser, зашифрованные файлы в `%LOCALAPPDATA%\Kasha\secrets`. API-ключи не должны попадать в обычные настройки или логи.

### Linux x64

Для Debian/Ubuntu используется DEB, для RPM-систем — RPM. Устанавливать пакет следует через системный пакетный менеджер, разрешающий зависимости. Создаётся ярлык приложения.

DEB объявляет `libnotify-bin` и `libsecret-tools`; RPM — `libnotify` и `libsecret`. Для уведомлений и Secret Service требуется работающая графическая пользовательская сессия с соответствующими службами. Отсутствие защищённого хранилища не должно включать небезопасное сохранение ключей.

Данные: `$XDG_DATA_HOME/kasha`, либо `~/.local/share/kasha`, если переменная не задана. Java, движки и базовые модели включаются в пакет.

### macOS

Текущий сборочный маршрут — Apple Silicon, macOS 13.3 и новее. Сборка Intel этим маршрутом не подтверждается. DMG содержит Kasha.app и ссылку на Applications. Подробная инструкция: [MACOS.md](MACOS.md).

## Запись, закрытие и восстановление

Запись, пауза, продолжение и завершение используют существующий Java Sound adapter. Исходное аудио записывается в WAV-журнал в `pending`; восстановление использует общий store. При ошибке сохранения журнал не удаляется. Переключение экранов не создаёт новый recorder.

Закрытие окна сначала вызывает сохранение общего состояния, затем закрывает desktop services. Поддерживаемая системная команда Quit направляется в тот же путь. Shutdown hook закрывает аудио-журнал при штатном завершении JVM; это не гарантия сохранения всех последних данных при отключении питания или принудительном уничтожении процесса.

Запрет одновременной записи и воспроизведения остаётся правилом общего application/UI-слоя. DesktopAudio не вводит собственные правила заметок или задач; он управляет только устройством вывода, загрузкой и временным аудиофайлом.

**Desktop-напоминания работают, пока приложение запущено.** Скрытый фоновый сервис, автозапуск и tray в этой реализации не добавлены. Показ уведомлений также зависит от разрешений и настроек ОС.

## Сборка разработчиком

Для установленного приложения отдельные Java и инструменты сборки не требуются. Разработчику нужны JDK 21, Gradle и инструменты, объявленные в workflows.

- Windows: `build-native-windows.sh` в MSYS2 UCRT64/MINGW64, затем `platforms/desktop/packaging/package-windows.ps1` в PowerShell. Workflow: `.github/workflows/desktop-platforms.yml`.
- Linux: `bash platforms/desktop/packaging/build-native-linux.sh`, затем `gradle :desktopApp:packageDeb :desktopApp:packageRpm`. Workflow: `.github/workflows/desktop-platforms.yml`.
- macOS: использовать `.github/workflows/macos.yml`; он готовит ресурсы, автономный app и DMG.

## Отложенная приёмка

После первичной реализации отдельно проверить физический микрофон и вывод звука, pause/resume и смену устройства, закрытие и повторный запуск, восстановление после сбоя, системные уведомления, установку/обновление/удаление на каждой ОС. Проверки на старом коммите не подтверждают новые изменения.

До успешной итоговой сборки и приёмки документ не объявляет production-релиз. Контрольные суммы и размеры пакетов берутся из артефактов конкретного успешного CI, а не из прежней версии инструкции.
