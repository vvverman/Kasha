## 1. Web: установленная причина и исправление

В артефакте `8141ec8` зарегистрирована последовательность второго `tidy`: HTTP 200, чтение 2070 байт, EOF в 37916,6 мс, затем AbortController в 37916,7 мс. Стек ведёт в Ktor JS. Это наблюдаемая отмена после полного чтения тела, а не недостаточный таймаут STT или ошибка модели.

В закреплённом Ktor 3.5.2 `commonFetch` подписывает AbortController на завершение callJob без проверки успешного EOF. Ранее один и тот же код мог дать зелёный прогон или `ERR_ABORTED`; повтор без изменений не считался исправлением.

Коммит `9c0e875` добавляет отдельный тонкий браузерный транспорт только для четырёх длинных POST-команд `process`, `retranscribe`, `tidy`, `rank`. Доменные правила, HTTP-контракт и состояние остаются прежними. CRUD-запросы не переписывались.

Новый адаптер принимает успех только после полного `response.text()` и не вызывает abort после успеха. Настоящая отмена или таймаут по-прежнему прерывают ожидание headers и тела. HTTP, сетевые и ошибки чтения отклоняют результат. Разрешён только origin приложения и прежний ограниченный dev-путь localhost:8080 → 127.0.0.1:8787; redirects запрещены, заголовок `X-Kasha-Client` сохранён. Текст не отправляется внешнему AI.

Локально и в CI прошли восемь новых сценариев: полное чтение без abort, отмена до headers, отмена тела, таймаут после headers, ошибки транспорта, запрет посторонних адресов, ограниченный dev-origin, независимость запросов. Всего Node: **64/64, без пропусков**.

[Kotlin/Web run 35748014722](https://github.com/vvverman/Kasha/actions/runs/35748014722), job `106814525090`, **`9c0e875`: completed / success**. Прошли сборки, архитектурные проверки, весь non-AI browser-набор, вкладки и AI readiness.

Проверен ZIP artifact **`10703903812`**, SHA-256 **`f32dc029c49748a938c456f6466eaeef86fbe820fd20174ca8610d08ce9d3fb0`**. XML: **58 suites, 410 тестов, 0 failures/errors, 2 skipped; 408 выполненных тестов**. Это конкретные отчёты этого SHA.

`capture-variants/result.json`: `passed=true`, `demoAi=true`, шесть сценариев; отправлены и полностью завершены **tidy → tidy → retranscribe → tidy**. Задержка первого ответа — 33 секунды. В `fetch-lifecycle.json` нового прогона нет abort-событий. Новый путь использует `Response.text()`, поэтому старый наблюдатель `getReader()` больше не считает байты этого пути; завершение подтверждают `requestfinished` и результат интерфейса, а не выдуманный EOF в этом журнале.

Успешны STT без автоматического Cleanup/routing, lazy-нормализация, кеш вкладок, отдельный повтор TEXT, отдельный принудительный STT и сброс устаревшего результата. Это настоящий shared Web UI с demo AI, **не оценка качества весов**.

## 3. Cleanup: источник проблемы уже проверен

Основной GGUF не менялся: `Kasha-Cleanup-0.6B-Q4_K_M.gguf`, **396 704 416 байт**, SHA-256 **`8c405ca3d29af67b21d2147e195b62ea63c84b84be1794b8aa453f31115b4f69`**. Это примерно 397 МБ, не первоначальная оценка 347 МБ.

Исходный snapshot `NicolaiMTLassen/transcrib-cleanup-0.6b` закреплён SHA **`881a17920f1a97e3adc155978188ad80c97bb0fb`**.

[Сравнение 35743091187](https://github.com/vvverman/Kasha/actions/runs/35743091187), `8141ec8`, завершило обе вычислительные ветки. Проверен artifact `10702845473`, ZIP SHA-256 **`3a127e46b12c09f0893de470c22c641154d0211243d513e99cb414f7806e9780`**. Двенадцать вызовов закончились с кодом 0, однако это **не зелёная оценка качества**.

Вход из трёх предложений содержит «Старый текст удалять нельзя». GGUF и контрольный расчёт из исходных весов теряют это содержание. Короткая фраза «Ирина не меняла 1200 пунктов» сохраняется. Самоисправление дня также обрабатывается ненадёжно.

Контрольный расчёт MLX использовал распаковку исходных 4-bit значений в float32 в памяти. Это **не прямой source-quantized runtime**: представление и арифметика отличаются. Нет обучения, повторного квантования или публикации новых весов. Результат позволяет отвергнуть гипотезу «достаточно исправить только упаковку GGUF», но не доказывает тождественность всех вычислений движков.

## 4. Текущий эксперимент — отдельно от main

Кодовые эксперименты **`438ff5d`**, затем **`4abcca6`** в `ai-cleanup-finish` проверяют:

1. Подготовку копии транскрипта: только явные однотипные числовые и календарные самоисправления RU/EN. Цитаты, часы вида 15:30, разные единицы и неоднозначные формы не угадываются. Сохранённый transcript не изменяется.
2. Разделение по границам предложений/абзацев с сохранением порядка и разделителей, без разрезания инициалов, сокращений, цитат или явного продолжения исправления. Уточнена граница после числа в конце предложения.
3. Настоящую генерацию каждого фрагмента, затем прежние проверки содержимого фрагмента и полного результата. Ошибка не подменяется скопированным исходником с флагом успешного Cleanup.
4. Общий таймаут нормализации; никаких новых AI-ролей, облачных обращений или других весов.

`CleanupLinesAcceptanceTest` вызывает действующие `LocalTextRoles` и `LocalLlm`, а не Python-имитацию нормализатора. Проверяет восемь синтетических случаев RU/EN/DE/UK, SHA-256 модели, сохраняет реальные запросы/ответы и факт ошибки. Процесс inference запускается с `sandbox-exec (deny network*)`; Gradle и подготовка зависимостей не выдаются за полностью изолированный запуск. Без явной переменной opt-in эти реальные тесты **пропускаются**, а не объявляются успешно выполненными.

Проверки общего кода должны пройти вместе с настоящим inference. Первый run — [35751902444](https://github.com/vvverman/Kasha/actions/runs/35751902444), `438ff5d`; второй относится к `4abcca6`. **На момент записи результаты этих экспериментов ещё не приняты.** Их нельзя сливать или объявлять готовым новым normalizer без просмотра ответов.

## Следующий шаг

Получить результаты `Cleanup lines acceptance` для последней экспериментальной ревизии. При подтверждённом улучшении перенести только проверенные изменения, выполнить полноценную macOS/Windows/Linux/iOS приёмку с настоящими моделями и указать точные SHA/run IDs. Если модель снова портит текст, не устранять failure ослаблением проверок и не объявлять защитный отказ успешно работающей нормализацией.
