## 1. Windows: исправлен реальный отказ диагностики

Это не повреждение моделей и не отсутствие файлов.

Артефакт `10690834735`, SHA-256 ZIP `1211ae27f8da1a26c3fe2ea9bbca52bb91a0d8042f4e92083250f528a98562da`, скачан и проверен.

Добавлены два настоящих subprocess-теста: успешный вывод и сообщение об отсутствующем файле при `PYTHONIOENCODING=cp1252`. Подменён только manifest с маленькими тестовыми файлами; код `main` и SHA-256 исполняются реально.

## 2. Linux: пропущен четвёртый исполняемый файл

На `c7b309c`, Linux job `106722782457` в `35720736025`, созданы DEB/RPM версии 1.2.0, DEB установлен. Последующий `--ui-smoke ... matrix` завершился по таймауту 120 секунд с кодом 124; AI-шаг пропущен. Сам таймаут не доказывает дефект модели.

В коде обнаружен конкретный пропуск: Linux `createDistributable` восстанавливал executable bit для whisper-cli, llama-completion и ffmpeg, **но не llama-embedding**. При этом `bundledEnvironment` уже требует исполняемый embedding CLI. Обычная ошибка startup могла показываться системным диалогом до входа в UI smoke.

Добавлен четвёртый CLI в тот же общий список прав; обход проверки или отключение embeddings не применяются. Перед UI smoke теперь запускается существующий `--install-smoke` именно установленного приложения, с ограничением 20 секунд и выводом лога при ошибке. Не меняются таймаут UI, запуск, переустановка, удаление или проверка сохранности данных.

Две новые статические регрессии проверяют полный список CLI и порядок `install-smoke` перед UI. Вместе с прежними и проверкой согласованности CAB **14 bundle-тестов прошли локально**. Это не доказательство успешной установки исправленного пакета; требуется CI следующей ревизии. В существующем desktop workflow `cancel-in-progress:false`, поэтому новый push не должен отменять выполняющуюся упаковку предыдущего SHA.

## 4. Web: успешный прогон и прерывистый ERR_ABORTED

На `c7b309c`, [Kotlin 35720735883](https://github.com/vvverman/Kasha/actions/runs/35720735883), job `106722780954`, второй обычный HTTP `tidy` получил статус 200, затем через 2 мс — `net::ERR_ABORTED`. Первый ответ с задержкой 33 секунды завершился успешно. Ошибок страницы или внешних запросов не было. Нельзя переносить прежний зелёный статус на этот прогон.

Проверен Web artifact `10691431921`, SHA-256 ZIP `90d2e2654990dc85e4a4a487ed6ac24d473abdb23abb1794c65c9a119fbf6909`. Исходники взяты из artifact `10690733714` той же ревизии, ZIP SHA-256 `8423229e5e6898d1e674d6822fc056cee222e5ce5bedc134fb85c805d6479adb`.

На `f3f04ae` [Kotlin 35740054278](https://github.com/vvverman/Kasha/actions/runs/35740054278), job `106787151470`, **completed / success**: сборки/тесты, весь non-AI browser-набор, вкладки и отдельная AI readiness-приёмка. Код Web между c7 и f3 не менялся: это подтверждает прерывистость, а не устранение причины. Модель в этих browser-сценариях демонстрационная.

Добавлен только тестовый наблюдатель `web_fetch_lifecycle_probe.js`: фиксирует Fetch, HTTP headers, число прочитанных байтов, EOF, отмену reader/AbortController и stack. Он не читает содержимое заметок, не добавляет второго читателя, не меняет Response и возвращает оригинальные Promise. События ограничены 500 строками и сохраняются отдельно в `fetch-lifecycle.json`.

Три Node-теста наблюдателя прошли локально: сохранность Promise/Response/байтов/EOF; неизменная передача отмены до EOF; отсутствие записи посторонних запросов. В браузерном тесте прежние assertions на `failures`, число команд и завершение HTTP **сохранены без исключений**.

Основание для наблюдения: в закреплённом Ktor 3.5.2 `commonFetch` вызывает AbortController при завершении callJob, а отменённый reader отменяет stream. Это возможное направление диагностики, не установленная причина данного сбоя. Требуется сопоставить EOF, abort и события браузера на реальном CI, прежде чем менять transport или интерпретацию ошибки.
