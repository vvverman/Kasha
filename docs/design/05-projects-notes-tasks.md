# 05. Проекты, заметки, задачи и выбор назначения

Этот документ задаёт целевой UX рабочих экранов Kasha: структуру, поведение данных, размеры, состояния и критерии передачи в разработку. Визуальные значения берутся из [основ](./02-foundations.md), общие контролы — из [компонентов](./03-components.md), транспорт записи и воспроизведения — из [сценария захвата](./04-capture-player.md). Здесь не создаются отдельная дизайн-система списков или второй проигрыватель.

## 2. Основные правила содержания

### 2.1. Одна запись — одно назначение

Один `Capture` сохраняется в одну заметку либо в одну задачу. В существующую заметку добавляется один блок в конец. Одна запись из пяти предложений не превращается автоматически в пять задач. Две команды «В заметки» и «В задачи» на результате являются альтернативными способами сохранить текущую запись.

После успешного сохранения capture перестаёт быть текущим несохранённым результатом. Повторный вызов сохранения того же capture возвращает уже созданный объект и не добавляет дубль. Смена назначения уже сохранённого источника этой версией не предлагается.

### 2.2. Единственный документ заметки

`Note.body` — единственное пользовательское текстовое поле. Первая непустая строка определяет название в списке, навигации и сортировке. Поле `Note.title` в модели — производное/совместимое поле, оно не получает отдельного input в интерфейсе. Аналогично отдельный title не появляется в редакторе задачи.

Текущий `NoteText.title()` обрезает производное название до 90 символов; `NoteText.preview()` пропускает первую непустую строку и берёт до 180 символов остального текста. Эти границы относятся к производным представлениям, а не к ограничению длины документа. Весь исходный текст остаётся редактируемым. Списки дополнительно применяют перенос и ellipsis по доступному месту.

Если документ содержит одну непустую строку, preview не дублирует её. Если текст очищен, поле остаётся доступным для ввода, а сохранение заблокировано с понятной причиной. Начальные пустые строки не создают название «Без названия» над существующим текстом.

### 2.3. Граница функций

Здесь нет отдельного раздела всех заметок вне проектов. Новая заметка создаётся в потоке сохранения результата; отдельная кнопка создания пустой заметки не добавляется без реализации соответствующего workflow. Задачи создаются из результата записи; свободный `+` из картинки не превращается в новую неподдерживаемую функцию.

В проверенных общих портах отсутствуют удаление проекта, удаление заметки, перенос заметки в другой проект и восстановление выполненной задачи. Эти команды не рисуются как работающие. У задачи есть фактическое удаление; оно описано ниже. Наличие glyph `Delete`, `Search` или `Archive` само по себе не означает наличие любого действия с любым объектом.

## 3. Общая композиция рабочих экранов

### 3.1. Плоскости и отступы

Рабочие списки спокойнее Главной. Их характер создают тёплая плоскость, шрифт и выверенный ритм. Сильный bloom, гигантский знак и активный orb здесь не используются. Полноэкранная фотография также не используется: отдельное уточнение про макрофон относится только к splash.

| Элемент | Компактный экран при стандартном размере текста |
|---|---|
| Горизонтальный внешний отступ | 20–24 dp; при очень узком окне допустимо 16 dp |
| Верхний отступ после системной safe area | 12–20 dp |
| Строка заголовка | Минимум 56 dp, высота растёт с текстом |
| Заголовок корневого раздела | H1 30/35; вложенного проекта — H2 25/30 при длинном названии |
| Кнопка справа/Back | Цель 48 × 48 dp, glyph 20–24 dp |
| От заголовка до сортировки | 12–16 dp |
| От сортировки до списка | 12–16 dp |
| Разделение логических групп | 20–24 dp; небольшая подпись группы при необходимости |
| Внутренний горизонтальный отступ строки | 14–16 dp |
| Внутренний вертикальный отступ строки | 14–16 dp, без фиксированного clip по высоте |
| Между ведущим glyph и текстом | 12–14 dp |
| Между заголовком и preview | 4–6 dp |
| Между preview и metadata | 6–8 dp |
| Нижний запас списка | Высота видимых player/nav + safe area + 16 dp |

Основное представление — строки на общей поверхности либо непосредственно на canvas, объединённые ритмом и очень слабым divider. Не требуется отдельная поднятая карточка для каждого элемента. Внутри одного экрана применяется одна модель: нельзя чередовать фон строки, толстую карточку и рамку без смысловой причины.

Divider начинается по колонке текста, а не пересекает glyph. Его декоративный hairline не служит единственным признаком кликабельности: помогают структура строки, disclosure, hover/focus и семантическая роль.

### 3.2. Scroll и навигация

Корневые вкладки сохраняют независимую позицию прокрутки; возврат из проекта, заметки, задачи или редактора восстанавливает прежний список и видимый элемент. Переход по вкладкам не останавливает запись или воспроизведение. На рабочих экранах транспорт виден в общей компактной панели.

Целевое сохранение контекста требует доработать текущий `navigate()`, который обнуляет вложенные выборы. Состояние маршрута и прокрутки хранится в общем UI-state с ключом объекта; оно не создаёт второй экземпляр доменных данных.

При исчезновении выбранного объекта после обновления не показывать пустую страницу. Сообщить «Заметка больше недоступна» / «Задача больше недоступна» и вернуть в ближайший доступный список. Несохранённый локальный текст до подтверждённого решения пользователя не выбрасывать.

## 4. Экран «Проекты» — P01

### 4.1. Назначение и структура

Экран отвечает на два вопроса: где лежат мысли и какой проект открыть. Верхняя строка: «Проекты» слева, Kasha Add справа. Под ней — «По дате изменения» или другой выбранный режим с glyph сортировки. Основное место занимает список.

Закреплённые проекты расположены сверху в порядке `pinOrder` во всех четырёх целевых режимах. Достаточно тонкого отступа между закреплёнными и остальными; большой контейнер «Избранное» не нужен. Если разделение неоднозначно при большом списке, допустима тихая подпись «Закреплённые» 13/18 перед группой. Если закреплены все проекты, отдельный пустой блок остальных не выводится.

### 4.2. Project row

| Слот | Содержимое и правила |
|---|---|
| Ведущий glyph | Project/Folder 22–24 dp; одинаковая геометрия у всех проектов |
| Название | Title 18/24, максимум 2 строки; целиком доступно после открытия и screen reader |
| Контекст | Body Small 14/20, максимум 1 строка в списке; сначала `instruction`, иначе legacy `description`; пустое поле не оставляет место |
| Закрепление | Малый pin 16–18 dp рядом с текстом; декоративный, не отдельная микрокнопка |
| Disclosure | Chevron 16–18 dp справа; весь ряд открывает проект |
| Контекстные действия | «Изменить проект» и pin/unpin через меню/контекстное действие; цель меню 48 dp, если кнопка показана |

Минимальная высота строки без описания — 64 dp; с одной строкой описания — примерно 80 dp. Длинное двухстрочное название увеличивает высоту, а не вытесняет доступную цель справа. При 200% текста все вертикальные ограничения становятся минимальными, trailing-команды не перекрывают текст.

В строке не показываются случайные количества заметок, «процент заполненности», дата последней активности AI или искусственные теги. Цвет glyph не кодирует тип проекта: пользователь такую модель не задавал.

### 4.3. Состояния

| Состояние | Отображение | Действие |
|---|---|---|
| Загрузка без данных | Небольшая текстовая индикация «Загружаем проекты»; структура шапки стабильна | Повторные мутации недоступны |
| Пусто | «Пока нет проектов»; ниже «Создайте проект, чтобы сохранять заметки по темам» | «Создать проект» |
| Есть данные | Список, актуальный сортировочный режим | Открыть, изменить, закрепить |
| Ошибка первого чтения | «Не удалось загрузить проекты» и «Повторить» | Не выдавать ошибку за пустой список |
| Ошибка обновления | Последний доступный список остаётся; компактное сообщение | «Повторить» |
| Сохраняется pin/order | Контроль занят; видимый новый порядок может быть временным до ответа | Повторная та же мутация блокируется |
| Ошибка pin/order | Возврат к подтверждённому состоянию; «Не удалось сохранить порядок» | Повторить осознанно, без скрытого цикла |

При первом запуске текущий `StudioState.launch()` создаёт «Твой первый проект», если список пуст. Редизайн не удаляет его и не заменяет название без отдельной миграции. Пустой экран всё равно нужен для ошибки/пустого snapshot и возможного будущего изменения onboarding; он не должен срабатывать на каждом обновлении списка.

## 5. Создание и редактирование проекта — P02

### 5.1. Форма

На узком экране — отдельная page. На широком — согласованная панель/диалог по правилам адаптивности. Заголовок «Новый проект» или «Изменить проект», Back слева. Поля расположены вертикально.

1. **Название проекта**. Однострочное редактируемое поле с минимальной высотой 56 dp; длинный ввод прокручивается внутри поля, без произвольного ограничения длины. Label снаружи, placeholder «Например, Работа» только как пример.
2. **Инструкция проекта (необязательно)**. Многострочное поле с минимальной высотой 132 dp. Подсказка: «Опишите, какие заметки относятся к проекту. Название тоже помогает выбрать проект».
3. **Сохранить**. Primary 56 dp, на компактном экране во всю доступную ширину. Между подсказкой и действием 24 dp.
4. Для существующего проекта — отдельная спокойная строка «Закрепить проект». После закрепления — доступные команды «Выше» / «Ниже» для порядка закреплённых; на границах соответствующая команда недоступна с понятной семантикой.

`description` остаётся совместимым полем существующей модели и при редактировании сохраняется. Новое второе похожее поле «Описание» рядом с «Инструкцией» не вводится.

### 5.2. Смысл инструкции

Инструкция помогает маршрутизации выбрать проект. Это не настройка отдельного чат-бота, не произвольный system prompt и не автоматическое разрешение отправлять текст внешнему сервису. Состав данных внешней маршрутизации раскрывается через [приватность](./06-settings-privacy.md).

Наличие инструкции не означает, что все новые записи автоматически сохраняются именно сюда. Пользовательский выбор проекта остаётся решающим; picker может предложить релевантность.

### 5.3. Ввод, ошибки и сохранение

Пустое или состоящее только из пробелов название не сохраняется. До первого действия поле не окрашивается ошибкой. После ухода из затронутого пустого поля/попытки сохранения под ним появляется «Введите название проекта». Ошибка имеет текст и glyph, цвет используется дополнительно.

Пробелы в начале и конце названия/инструкции Core удаляет при сохранении; пробелы внутри текста сохраняются. Одинаковые названия сейчас допускаются, поэтому нельзя показывать ложную ошибку уникальности. При нескольких одинаковых названиях пользователь видит их инструкции и может открыть нужный проект; нельзя тайно добавлять суффикс к пользовательским данным.

Во время сохранения кнопка показывает «Сохраняем» с компактным индикатором, сохраняет ширину и не меняет высоту. Исходный ввод остаётся до успешного ответа. При ошибке фокус не прыгает к началу формы, текст и scroll остаются; сообщение «Не удалось сохранить проект. Попробуйте ещё раз» располагается рядом с действием.

Back, закрытие панели и смена вкладки при изменённой форме показывают один диалог: «Сохранить изменения?» с «Сохранить», «Не сохранять», «Продолжить редактирование». Это целевая защита ввода; текущий `remember()` и немедленный `cancelProjectEdit()` её не обеспечивают. При неизменённой форме возврат происходит сразу. Системное скрытие клавиатуры сначала скрывает IME и само по себе не отменяет форму.

Закрепление существующего проекта сейчас сохраняется отдельным действием сразу. В целевом UI оно сохраняется сразу и не входит в текстовый dirty-state: после переключения показывается подтверждённое состояние, ошибка откатывает только закрепление. Кнопка «Не сохранять» при выходе отменяет текстовые правки, а не уже подтверждённый pin.

### 5.4. Создание из выбора назначения

Создание проекта, начатое из picker текущей записи, после успешного сохранения возвращает к выбору заметки внутри нового проекта. Оно не создаёт заметку автоматически. Если пользователь закрывает форму, возвращается к списку проектов с тем же capture и текстом.

Привязка возврата делается по исходному `captureId`, как в `creatingForCaptureId`. Запоздавший ответ создания проекта не должен открыть назначение для уже другой записи или неожиданно переключить вкладку после самостоятельной навигации пользователя.

## 6. Выбор назначения заметки — N01/N02

### 6.1. Вход

Результат → «В заметки» → сохранение актуального текста → маршрутизация → выбор проекта. Это последовательность существующего `sendToNotes()`. «Привести в порядок» перед сохранением необязательно.

До открытия picker актуальный текст должен быть сохранён через `flush()`. Не сортировать проекты по AI-оценкам от предыдущей редакции текста: правки сбрасывают `rankingApplied` и `relevance`. Во время получения оценки состояние сообщает «Подбираем проекты», без fake percentage и без отображения старых рекомендаций как свежих.

При недоступной маршрутизации целевое улучшение — разрешить ручной выбор проекта с сообщением «Не удалось подобрать проект. Выберите его сами». Это изменение существующего `sendToNotes()`, где ошибка `rank()` сейчас прерывает открытие picker; оно должно использовать существующий список, не вызывать внешнего провайдера без согласия и не изменять текст записи.

### 6.2. N01 — выбор проекта

Шапка «Выберите проект», Back возвращает к результату. Под шапкой — «Создать проект» как Secondary/Quiet с Add, без конкуренции по яркости с будущим сохранением. Ниже список доступных проектов.

Сортировка picker отличается от экрана «Проекты» и не изменяет его preference:

1. Закреплённые в `pinOrder`.
2. Остальные — по убыванию подтверждённой релевантности `relevance`.
3. При равной релевантности — текущий алфавитный tie-break из Core; затем `id`.

AI-оценки 0–4 в модели не являются вероятностью в процентах. Не выводить «Подходит на 97%». Допустима единичная подпись «Подходит по содержанию» у ненулевой подтверждённой рекомендации, если продуктовая реализация однозначно отличает её от просто первого проекта. В отсутствие валидной оценки никаких рекомендационных badges не показывать.

Нажатие строки только выбирает проект и открывает N02. Оно не сохраняет capture. Reorder и общий Sort здесь отсутствуют, чтобы не смешивать управление своей коллекцией с выбором места сохранения.

Если проектов нет, показать объяснение и «Создать проект»; текущее содержимое сохраняется. При ошибке списка остаются Back и повтор чтения; нельзя предлагать создание одноимённого проекта как единственный способ избежать ошибки.

### 6.3. N02 — новая или существующая заметка

Шапка — название выбранного проекта; Back возвращает к N01, не на Главную. Под ней Primary «Новая заметка» с Add. Под кнопкой через 20–24 dp текст «Или добавить в конец существующей заметки». Ниже заметки этого проекта в пользовательском режиме `noteSort`, без ручного перетаскивания.

Строка существующей заметки сохраняет знакомую структуру title/preview/date. В этом контексте её accessible label: «Добавить текст в конец заметки „…“», а не «Открыть заметку». Контекстная команда pin или edit здесь не появляется.

Перед первой строкой ясно написано, что нажатие сохраняет. После нажатия вся область выбора блокирует повторную отправку, выбранный ряд получает компактный индикатор; Back и переключение назначений не запускают вторую операцию. При больших списках текущая строка остаётся на месте до результата.

Если проект пуст, остаётся «Новая заметка» и короткий текст «В этом проекте пока нет заметок». Не показывать пустой блок append с длинным объяснением.

### 6.4. Контракт сохранения и возврата

| Действие | Изменение данных | Результат интерфейса |
|---|---|---|
| «Новая заметка» | Создать одну `Note`, связать capture с `noteId`, записать `appendedAt` | Открыть список выбранного проекта; показать «Заметка сохранена» с действием «Открыть» |
| Нажать существующую заметку | Добавить `\n\n` и очищенный добавляемый текст к прежнему body; связать источник | Тот же список; сообщение «Добавлено в заметку „…“» и «Открыть» |
| Повторить после неизвестного результата | Проверить сохранённую связь исходного capture; идемпотентно получить тот же объект | Не создавать второй документ/блок |
| Ошибка сохранения | Не объявлять успех; capture и редактируемый текст остаются | Остаться в N02, вернуть доступность выбора и «Повторить» |
| Целевой проект/заметка недоступны | Не подменять назначение первым элементом списка | Сообщить причину и вернуть к выбору доступного назначения |

Переход в список проекта соответствует нынешнему `distribute()`. Выделение сохранённой строки на 600–900 ms — допустимая локальная подсветка без скролла через весь список, если пользователь уже успел взаимодействовать. Action «Открыть» ведёт непосредственно к сохранённой заметке. В сортировке по изменению она окажется в соответствующей части списка; в Manual её не вытягивают наверх вопреки порядку.

Append не переписывает старый текст, не объединяет предложения AI-моделью, не заменяет заголовок новой фразой и не удаляет старое аудио. Новая первая строка получается только при прямом редактировании самого документа. У одного документа может быть несколько источников; каждому соответствует отдельный capture.

## 7. Заметки проекта — N03

### 7.1. Экран

Шапка содержит Back, название проекта и «Изменить проект» в More. Для длинного названия отводится до двух строк; полный текст доступен при открытии редактора и через семантику. Под шапкой — текущая сортировка. Отдельный большой подзаголовок «Заметки» допустим только если нужен смысловой контекст на широком экране; на телефоне название проекта и список достаточно ясны.

### 7.2. Note row

| Слот | Значение |
|---|---|
| Название | Первая непустая строка, Title 18/24, 1–2 строки |
| Preview | Остальные непустые строки, Body Small 14/20; стандартно 2 строки, до 3 в просторном режиме |
| Дата изменения | Label 13/18: «Сегодня, 14:32», «Вчера, 09:10» либо абсолютная дата |
| Аудио | Небольшой audio glyph 16–18 dp, только если есть связанный доступный/известный аудиоисточник |
| Закрепление | Малый pin; не создаёт отдельную текстовую колонку |
| Открытие | Вся строка; общая доступная цель минимум 48 dp по высоте |

Для одной строки без preview размер строки примерно 76–84 dp с metadata; для двухстрочного preview — примерно 116–132 dp. Это ориентиры ритма, а не жёсткие высоты. Текст в списках не уменьшается для вместимости. Снизу каждой строки не создаётся большой плеер: audio glyph обозначает наличие источника, прослушивание открывается из заметки.

Если аудиоссылка существует, а доступ к файлу потерян, не показывать декоративную waveform как будто файл доступен. В списке допустим audio glyph с доступным описанием «Аудио недоступно»; причина и повтор доступны внутри заметки.

### 7.3. Закрепление заметок

Существующее закрепление заметки сохраняется. Целевое улучшение согласованности D-31/GAP-15 распространяет принцип проектов на заметки: закреплённые заметки идут первыми в `pinOrder` внутри проекта во всех четырёх режимах; в Manual остальные следуют своему `manualOrder`. Сейчас Core выполняет эту группировку только в автоматических сортировках. Изменение вводится в общем правиле, не локально в списке Compose.

Полная прежняя ручная последовательность сохраняется независимо от закрепления. Pin/unpin не стирает позицию заметки, куда она вернётся после снятия закрепления. В Manual перетаскивание закреплённой заметки меняет только `pinOrder`, обычной — её положение среди незакреплённых. Через границу групп нельзя незаметно закрепить или открепить заметку.

Для порядка закреплённых заметок требуется новый общий контракт, например `orderNotePins(projectId, ids)`, и реализация repository adapters. Его сейчас нет в `Ports.kt`: это целевое требование, а не существующий метод. Он принимает все закреплённые заметки указанного проекта ровно один раз, не затрагивает другой проект, body, timestamps и manualOrder. Доступные команды «Выше» / «Ниже» действуют внутри этой группы и появляются в том же меню перемещения, что у проектов.

### 7.4. Пустое и ошибочное состояния

Пустой проект: «Пока нет заметок» и «Запишите мысль на Главной и сохраните её в этот проект». Команда «На Главную» ведёт туда без автоматического запуска записи и не создаёт несуществующую пустую заметку. Если уже есть несохранённый результат, можно предложить «К тексту записи» — это тот же Home и текущий capture.

Ошибка обновления не превращает список в «Пока нет заметок». Уже загруженные строки остаются, доступно повторное чтение. Если сохраняется перестановка, соседний pin или обновление snapshot не должны сбросить локальную последовательность посреди gesture.

## 8. Заметка и редактирование — N04

### 8.1. Чтение

Порядок блоков: header → единый документ → аудиозаписи → metadata. Глобальный плеер принадлежит оболочке, а не копируется в конец каждой заметки.

В header: Back; справа pin/unpin и при необходимости тихое действие «Изменить». Длинное название не дублируется большим заголовком над первой строкой документа. В компактной верхней панели допустимо сокращённое производное название для навигации; при отсутствии места используется подпись «Заметка». Первая строка body остаётся частью того же документа.

Сам текст: Body 16/23 или Body Large 17/25 согласно читательскому режиму из foundations; колонка не растягивается без ограничения на широком окне. Текст лежит на одной спокойной Surface с внутренним отступом 18–20 dp либо на canvas по единому правилу редактора. Здесь нет декоративной рамки вокруг каждого абзаца.

Тап по тексту активирует редактирование в том же месте. Вся заметка остаётся одним input; текст можно выделять, копировать и править системными средствами. Нельзя превращать первую строку в отдельный узел редактирования, если это ломает Backspace/Enter, выделение нескольких строк или IME. Отдельная кнопка «Изменить» остаётся доступной альтернативой тапу по тексту.

### 8.2. Редактирование

При входе не перестраивается вся страница и не прыгает scroll. Курсор ставится в место касания, при открытии командой — в сохранённую позицию либо в конец. На desktop фокус виден; Tab не вставляет невидимый символ вместо перехода без согласованной поддержки редактора.

Нижняя область действий: Quiet «Отменить» и Primary «Сохранить». Кнопка доступна при непустом изменённом body; при неизменённом тексте выход не создаёт лишнего `updatedAt`. Это целевая доработка нынешнего редактора. Клавиатура не накрывает действия и последнюю строку; область документа имеет собственный корректный scroll/IME inset.

Рабочая копия отделена от подтверждённого snapshot. Поступление нового snapshot, смена темы, системного размера текста, поворот экрана, сворачивание sheet и изменение раскладки не обнуляют введённые символы, selection и позицию прокрутки. У задачи нынешний `remember(task.id, task.updatedAt)` также не должен сбрасывать текст вслед за фоновым обновлением.

| Событие | Требуемое поведение |
|---|---|
| Непустая правка | Обновить локальный body и производное название, не сохранять отдельный title |
| Всё удалено | Оставить input; «Сохранить» недоступно; после попытки выхода предложить вернуться или отменить правки |
| «Сохранить» | Передать полный body; показать занятую кнопку; закрыть editing-state только после подтверждения |
| Ошибка | Сохранить ввод/курсор; текст «Не удалось сохранить заметку. Изменения остаются здесь»; повтор |
| Back/вкладка с правками | «Сохранить изменения?»; никакого немого `cancelNoteEdit()` |
| «Отменить» при правках | Подтвердить отказ от несохранённых изменений; подтверждённый body восстановить |
| Обновление исходника извне | Не перезаписывать рабочую копию; показать «Заметка изменилась. Проверьте текст перед сохранением» при реальном конфликте |

Локальная защита ввода — требование UX, не обещание существующей системы версий/синхронизации. Новые экраны истории или сравнения версий не вводятся.

### 8.3. Metadata

Ниже текста и аудио спокойными строками: «Создана …» и «Изменена …». На основную карточку списка выводится только дата изменения. Metadata берётся из фактических полей, без счётчиков слов и псевдометрик. `updatedAt` заметки меняется при редактировании body и append; pin/unpin не изображается как изменение содержания.

### 8.4. Аудиозаписи заметки

Блок показывается только при наличии связанных источников. Заголовок «Аудиозаписи», подсказка «Выберите запись для плеера». Между документом и блоком 24–28 dp; между источниками 8–12 dp либо внутренние divider общей поверхности.

Источник — строка минимум 64–76 dp: короткое название/дата записи, реальная waveform высотой 28–36 dp и длительность справа с tabular figures. Waveform имеет ту же геометрию и семантические цвета, что общий player; она не генерируется случайно ради наполнения.

Порядок — по `appendedAt` от раннего к позднему, как `noteSources()`. При одинаковых значениях UI сохраняет стабильный порядок; для неполных legacy-данных общий детерминированный tie-break должен использовать `createdAt`, затем `id`, без изменения самих временных меток.

Нажатие выбирает источник в единственном player и запускает воспроизведение согласно общему транспортному правилу. Активный источник получает маленький текстовый статус «Воспроизводится» или «Пауза» и выделение; один цвет без статуса недостаточен. Редактирование заметки не перезаписывает исходный аудиофайл или сохранённый текст capture.

Если идёт запись либо запись на паузе, нажатие не начинает playback одновременно. Подтверждение «Завершить запись и начать прослушивание?» с пояснением «Текущая запись останется на Главной» имеет «Завершить и слушать» и «Отмена». Отмена сохраняет прежнее состояние recording/paused: запись на паузе не возобновляется. При подтверждении сначала успешно завершается/сохраняется захват, затем запускается аудио. При ошибке завершения playback не начинается.

| Состояние источника | Отображение |
|---|---|
| Доступен | Реальная длительность и waveform, действие воспроизведения |
| Нет рассчитанных peaks, файл доступен | Длительность и обычный glyph; строка «Аудиозапись» без выдуманных амплитуд |
| Загружается/открывается | Занят именно выбранный источник, другие команды не создают второй transport |
| Нет файла/отказ доступа | «Аудио недоступно», понятное повторное действие; текст заметки остаётся читаемым |
| Ошибка проигрывания | «Не удалось воспроизвести запись»; повтор, без сброса документа |

## 9. Сортировка и ручной порядок — O01/O02

### 9.1. Один компактный Sort control

На экране постоянно видна одна команда: glyph Sort и текущий режим, например «По дате изменения». Touch target минимум 48 dp по высоте. По нажатию открывается sheet на узком экране или popover на широком. Заголовок «Сортировка»; четыре строки минимум 56 dp по общему radio-компоненту, выбранная с check и семантикой selected.

| Режим в интерфейсе | Правило Core | Дополнительное пояснение |
|---|---|---|
| По алфавиту | По возрастанию `title.lowercase()`; для заметок title получен из body, для задач используется полный `text.lowercase()` | Текущая реализация не обещает словарную сортировку «Ё» или чисел 2/10 по locale |
| По дате создания | Новые первыми | Дата создания объекта, не дата исходного аудиофайла |
| По дате изменения | Недавно изменённые первыми | Для проекта `updatedAt`, при отсутствии — `createdAt` |
| Вручную | Сохранённые `manualOrder` с целевой группировкой проектов по D-22 и заметок по D-31 | Текстовая подсказка о перемещении; handles появляются только при взаимодействии |

Выбор режима сразу сохраняется в preferences, закрывает picker и обновляет список без возврата к началу, если текущий элемент можно оставить видимым. Ошибка сохранения возвращает старый режим и показывает конкретное сообщение. Screen reader слышит «Сортировка: по дате изменения», а не только «Sort».

Сейчас существуют три preferences: `projectSort`, `noteSort`, `taskSort`. `noteSort` общий для списков всех проектов, `taskSort` общий для активных и архива. Не создавать отдельные preferences на каждый проект или архив только внутри UI. Ручной порядок заметок при этом хранится отдельно в каждом проекте.

### 9.2. Порядки не перезаписывают друг друга

| Хранимое поле | Где применяется | Что не должно его менять |
|---|---|---|
| `Project.manualOrder` | Пользовательская последовательность проектов; в целевом Manual отображаются незакреплённые в этом порядке | Алфавит/даты, pin/unpin, открытие picker, AI-рейтинг |
| `Project.pinOrder` | Закреплённые проекты во всех режимах | Ручная перестановка обычных проектов |
| `Note.manualOrder` | Полная ручная последовательность заметок внутри проекта; в целевом Manual отображаются незакреплённые в этом порядке | Смена sort, pin/unpin, редактирование body |
| `Note.pinOrder` | Закреплённые заметки во всех целевых режимах | Ручная перестановка обычных заметок |
| `Task.manualOrder` | Активные задачи; у выполненных сохраняется последнее значение | Смена sort, расписание, автоматическое напоминание |

Новый проект/заметка/активная задача получает позицию после существующих в своей ручной последовательности, как нынешние Core-методы. При одинаковых значениях применяется детерминированный `id` tie-break. Закрепление добавляет объект в конец текущей группы закреплённых; снятие закрепления не уничтожает прежнюю manual-позицию.

### 9.3. Целевой Manual проектов

Это обязательное изменение Core по D-22/GAP-09. `UserSort.projects(MANUAL)` возвращает закреплённые по `pinOrder`, затем остальные по `manualOrder`. UI не группирует локально поверх старого результата: правило должно одинаково работать на всех платформах и в тестах.

При перетаскивании закреплённого проекта меняется только `pinOrder`. При перетаскивании обычного — только порядок незакреплённых в общей сохранённой manual-последовательности. Позиции скрытых из этой группы закреплённых проектов сохраняются: реконструировать полный список можно, заменив элементы только в тех слотах прежнего `manualOrder`, которые принадлежат незакреплённым. Нельзя отправлять в нынешний `orderProjects()` неполный список — Core требует все ID ровно один раз.

Перетаскивание через границу закреплённых и обычных не меняет pin неявно. Строка останавливается у границы, короткая подсказка «Сначала снимите закрепление» или «Закрепите проект, чтобы переместить его выше». Не добавлять автоматический диалог в середине gesture. Явное pin/unpin доступно в контекстном меню/редакторе.

Для заметок алгоритм тот же внутри `projectId` по D-31: обычные заметки заменяют только обычные слоты полного сохранённого manual-порядка; закреплённые меняют свой pin-порядок новым общим контрактом. Существующий `orderNotes(projectId, ids)` по-прежнему требует весь состав заметок проекта. Миграция не обнуляет поля и не сортирует документы по title для восстановления потерянных позиций.

### 9.4. Long press, drag и drop

Только в Manual удержание вне вложенной кнопки запускает drag после системного порога long press. Обычное вертикальное движение до удержания прокручивает список; тап открывает объект. Удержание текста в самом редакторе остаётся выделением текста, не перестановкой.

Lift: один haptic при доступности; scale 1.015; повышение до Surface Highest; мягкая тень; появляется временный drag glyph. Исходное место сохраняет размер; соседние строки меняют положение пружиной. Не использовать только alpha .72 как обратную связь вместо ощущения поднятого элемента.

При пересечении центров соседних строк меняется ожидаемая позиция и подаётся один haptic на фактическую смену индекса; движение внутри той же позиции не щёлкает. Автопрокрутка включается в верхней/нижней краевой зоне 48 dp видимого списка, ускоряется по приближению к краю и не попадает под nav/player.

Drop: scale возвращается в 1, вызывается одна операция сохранения полной валидной последовательности. После ответа снимается состояние сохранения. Cancel gesture/Escape восстанавливает порядок на момент lift и ничего не сохраняет. Ошибка сохранения возвращает подтверждённую последовательность, удерживает фокус на той же сущности по ID и сообщает причину.

Во время активного drag внешний snapshot не подменяет объекты по индексам. После завершения результат согласуется по ID; если состав списка изменился, не отправлять устаревший неполный список. Сообщить «Список изменился. Попробуйте переместить ещё раз» и восстановить актуальные данные.

### 9.5. Доступная альтернатива

Каждый перемещаемый ряд в Manual имеет screen-reader custom actions «Переместить выше» / «Переместить ниже». Контекстное меню и клавиатурный вызов меню предлагают те же действия. Обычные Tab и стрелки не перехватываются неожиданно: сначала пользователь открывает режим/меню перемещения. Escape отменяет начатую перестановку.

После действия фокус остаётся на перемещённом объекте. Объявление: «Проект „Работа“, позиция 2 из 5»; для закреплённой группы — «Позиция 2 из 3 закреплённых». На первой/последней позиции недоступное направление имеет disabled semantics. Для мыши допустим временный handle при hover/focus, с целью 44–48 dp; на обычном мобильном экране постоянные handles отсутствуют.

В архиве задач режим сортировки Manual может показывать сохранённый порядок, но перестановка выключена: нынешний `orderTasks()` принимает только активные задачи. Подсказка «Порядок сохранён при выполнении. Перемещение доступно в активных задачах» появляется при выборе Manual архива, а не на каждой строке.

## 10. Активные задачи — T01

### 10.1. Композиция

Шапка «Задачи», справа действие «Архив» с glyph Archive и доступным названием. Под ней — текущая сортировка. Список не разбивается самовольно на «Сегодня», «Неделя», «Проекты» и «Приоритет»: такие фильтры на изображении не подтверждены текущим workflow.

Никаких assignee, priority, tags, progress percent, comments и декоративных статусов. В строке только выполнение, текст, срок и маркер напоминания.

### 10.2. Task row

Слева Kasha completion glyph 22–24 dp внутри отдельной цели 48 × 48 dp. Справа текст: Title 18/24 или Body Large 17/25 при длинном тексте, до двух строк в стандартной строке; ниже срок 13/18 и reminder marker 16–18 dp. Минимальная высота 76–84 dp, увеличивается с текстом и масштабом. Строка сама открывает задачу, completion действует отдельно и не передаёт нажатие родителю.

Сокращённый текст в списке берётся из первой непустой строки до 90 символов, как текущий `taskTitle()`; в деталях доступен полный `Task.text`. Несколько абзацев/пунктов внутри задачи не получают отдельные completion controls.

Маркер напоминания обозначает заданное расписание, а не гарантированную доступность уведомления ОС. Если системные уведомления недоступны, уместен один компактный статус над списком или в редакторе, без повторения предупреждения в каждой строке.

### 10.3. Выполнение из строки

1. Нажатие меняет glyph в pressed-state и запускает существующий `completeTask(id)`.
2. До успешного ответа строка остаётся, повторное выполнение заблокировано.
3. После подтверждения контур morph в filled/check за 220–320 ms, один haptic при доступности; подпись становится чуть спокойнее, но сохраняет читаемость.
4. После короткой видимой фиксации, ориентир 250–400 ms, строка уходит из активных в архив с мягким перераспределением места.
5. Сообщение «Задача выполнена» может содержать «Открыть архив». «Отменить» не предлагается: восстановления в Core пока нет.

Не держать исчезнувшую строку в доступном дереве после окончания анимации. Фокус переводится на следующую задачу, при её отсутствии — на предыдущую, при пустом списке — на заголовок/пустое состояние. Screen reader слышит «Задача выполнена, перемещена в архив». При ошибке glyph возвращается в исходное состояние, задача не исчезает; «Не удалось выполнить задачу» и повтор.

Текущий UI выполняет задачу только в деталях; строковый control — целевой UI над существующим предметным действием. Это не новый тип сущности и не «проверить пункт списка» внутри текста.

### 10.4. Пустое состояние

«Пока нет задач». Подпись «Запишите задачу на Главной и выберите „В задачи“». Команда «На Главную» не запускает запись автоматически. После выполнения последней задачи — «Все задачи выполнены» и тихое «Открыть архив»; это определяется текущим наличием выполненных задач, без выдуманного достижения/конфетти.

Ошибка загрузки имеет собственное сообщение и повтор, список не маскируется под пустой. Отсутствие разрешения уведомлений не делает список задач недоступным.

## 11. Задача и редактор — T02/T03

### 11.1. Единый предметный объект

При открытии активной задачи показываются header, единый редактируемый текст, «Срок и первое напоминание», «Повторять напоминание», действия. На узком экране длинный текст редактируется на отдельной page; компактное расписание допустимо в bottom sheet с корректным IME/scroll. На широком экране — одна панель с теми же полями.

Четыре понятия пользовательского ТЗ — текст, срок, напоминание, повтор — отражаются без ложной независимости полей: в стартовой модели первое напоминание равно сроку. Поэтому UI использует комбинированную группу «Срок и первое напоминание» и отдельную частоту повторов. Кнопка выключения/«Без напоминания», независимое `reminderAt` и «Без срока» здесь не рисуются: `TaskDistributionRequest`/`TaskScheduleUpdate` этого не описывают.

### 11.2. Новый объект из capture

«В задачи» сохраняет актуальный текст capture и открывает единый редактор новой задачи: один непосредственно редактируемый текст, срок и первое напоминание, повтор. Это целевое улучшение существующего `TaskScheduleScreen`, где сейчас есть только расписание. Текст связан с текущим capture через общее редактирование `editText()` и подтверждается `flush()` перед сохранением; отдельное поле title и второй независимый текстовый state задачи не создаются. Проект выбирать не требуется; существующий `sendToTasks()` не вызывает проектную маршрутизацию. `projectId` у новой задачи может остаться `null`.

До нажатия «Сохранить задачу» задача не создаётся. Back/закрытие возвращает к тому же результату, не теряя текст. Поменянное расписание в рамках ещё открытого потока сохраняется локально до подтверждения выхода; никакой скрытой задачи в архиве не возникает.

При успешном сохранении создаётся одна `Task`, capture получает `taskId` и перестаёт быть текущим результатом. Открывается активный список задач и сообщение «Задача сохранена». Двойной тап и повтор запроса не создают копии. Audio source остаётся связанным через capture: создание задачи не выбрасывает файл.

Текущие детали задачи не имеют списка аудиоисточников, аналогичного заметке. Сохранение связи обязательно; отдельный новый player внутри task editor в этой версии не добавляется. Пользовательский интерфейс не обещает воспроизведение из задачи до реализации такого маршрута.

### 11.3. Редактирование существующей задачи

Текст меняется в одном документе. Под текстом сводка: «Срок: 14 сентября, 15:30» и «Напоминать каждый час». Действие «Изменить срок и напоминание» открывает T03. Изменение расписания не переписывает Task.text и не сбрасывает несохранённые текстовые правки.

При изменённом тексте доступно «Сохранить». «Выполнить задачу» также допустимо; оно сначала сохраняет непустую рабочую копию и только после подтверждённого успеха выполняет задачу. Если сохранение не удалось, выполнение не вызывается. Текущую последовательность `saveTask(); completeTask()` требуется сделать зависимой от результата, а не продолжать после пойманной ошибки.

Back и закрытие с изменённым текстом используют тот же диалог защиты, что заметка. Пустой текст не сохраняется; завершение также недоступно, пока пользователь не восстановит содержание или не отменит правки.

Внизу есть Quiet destructive «Удалить задачу». Удаление не конкурирует по яркости с «Выполнить». Полная заливка Error используется только для подтверждённого destructive action в диалоге согласно общей системе компонентов.

### 11.4. T03 — дата, время и повтор

Дата и время имеют внешние labels «Дата» и «Время». Минимальная высота каждого поля 56 dp, gap 10–12 dp. В компактном стандартном окне дата занимает остаток, время минимум 112–128 dp; при 200% они становятся вертикальными на полную ширину. Форматы ручного ввода текущего Core: `ДД.ММ.ГГГГ`, `ЧЧ:ММ`. Placeholder не заменяет label.

Начальное значение для новой задачи — текущий момент + один час. Значение вычисляется один раз при открытии потока, не на каждой recomposition. Нынешнюю привязку `remember(target, initialDue)` необходимо стабилизировать: изменение текущих секунд не должно самопроизвольно сбрасывать ввод.

Срок должен быть строго в будущем и повторно проверяется в момент сохранения, а не только при отрисовке. Если пользователь долго редактировал и время уже прошло, показывается «Укажите будущие дату и время»; ввод остаётся. Если календарная дата/время синтаксически неверны, сообщение точнее: «Проверьте дату» / «Проверьте время». На первой отрисовке корректного начального значения ошибок нет.

Ниже через 24 dp группа «Повтор напоминания». Семь radio-строк на общей поверхности, минимум 56 dp каждая. Выбранное значение имеет check и selected semantics; остальные не выглядят disabled.

| Значение Core | Текст интерфейса | Смысл |
|---|---|---|
| `TEN_MINUTES` | Каждые 10 минут | Следующее напоминание через 10 минут после обработки текущего |
| `THIRTY_MINUTES` | Каждые 30 минут | Через 30 минут |
| `HOURLY` | Каждый час | Через 60 минут; исходное значение новой задачи |
| `DAILY` | Ежедневно | Следующий календарный день от момента обработки, в текущем часовом поясе |
| `WEEKLY` | Еженедельно | Через 7 календарных дней от момента обработки |
| `WEEKENDS` | По выходным | Следующие суббота/воскресенье после текущего дня обработки |
| `WEEKDAYS` | По будням | Следующий понедельник–пятница после текущего дня обработки |

Под группой: «Повторяется напоминание об этой задаче. Новые задачи не создаются». Для новой задачи первое уведомление назначается на выбранный срок даже при выборе «По будням» на субботнюю дату: частота применяется к последующим напоминаниям. Не обещать календарный фильтр первого срока, которого нет в Core.

Закреплённое нижнее действие: «Сохранить задачу» для новой; «Сохранить изменения» для существующей. Кнопка disabled при неверном времени или busy. Загрузка не закрывает sheet раньше успешного ответа; ошибка не стирает введённую дату и повтор.

## 12. Напоминания, перенос срока и календарь

### 12.1. Что сейчас делает Core

Поля задачи: `dueAt` — срок, `nextReminderAt` — следующий момент напоминания, `reminderRepeat` — частота, `completedAt` — выполнение. При создании и явном изменении расписания `nextReminderAt = dueAt`. Выполнение ставит `completedAt` и обнуляет `nextReminderAt`.

`claimDueReminders(now, zoneId)` выбирает активные задачи, у которых `nextReminderAt > 0 && nextReminderAt <= now`. Для каждой атомарно:

1. Переносит уже наступивший `dueAt` на ближайший последующий календарный день в том же локальном времени, пока срок не окажется строго позже `now`.
2. Вычисляет следующее напоминание **от фактического `now`**, по выбранному `ReminderRepeat`.
3. Возвращает для уведомления исходную версию наступившей задачи.

Это не постоянный ежедневный фоновый процесс и не создание новой задачи. Перенос происходит при обработке наступившего напоминания доступным адаптером/общим workflow. Если приложение/адаптер не вызывает claim, одна лишь смена даты на часах не гарантирует уже сохранённого переноса.

### 12.2. Как объясняем пользователю

В редакторе под сводкой расписания короткий текст: «Если срок наступит, а задача не выполнена, Kasha перенесёт его на ближайший следующий день в то же время. Напоминания продолжатся с выбранной частотой». Дополнительное пояснение раскрывается по «Как это работает», без отдельного нового раздела продукта: «Перенос выполняется при обработке напоминания. Возможность уведомлять при закрытом приложении зависит от устройства».

Не выводить на строке вечный красный статус «Просрочено», если Core уже изменил срок. Пока время наступило, но claim ещё не произошёл, доступен нейтральный текст «Срок наступил»; это фактическое состояние, без тихого локального пересчёта dueAt только для картинки.

Если при открытом экране приложение наблюдает подтверждённое изменение dueAt после claim, допускается одно сообщение «Срок перенесён на 15 сентября, 15:30». Постоянная плашка «Перенесено» требует истории, которой в модели нет, поэтому не показывается после перезапуска по догадке.

### 12.3. Примеры для проверки

| Условия в одном часовом поясе | Результат Core |
|---|---|
| Срок 14 сентября, 15:30; claim ровно в 15:30; каждый час | Новый срок 15 сентября, 15:30; следующее напоминание 14 сентября, 16:30 |
| Тот же срок; приложение обработало в 15:37 | Новый срок 15 сентября, 15:30; следующее напоминание 16:37 |
| Приложение не открывалось до 17 сентября, 16:00 | Срок последовательно двигается до 18 сентября, 15:30; приходит одно обработанное напоминание на задачу, без каскада за пропущенные часы |
| Следующее напоминание 14 сентября, 16:37; срок уже 15 сентября, 15:30 | Claim меняет только nextReminderAt; будущий dueAt не сдвигается ещё на день |
| Повтор «По выходным», claim в пятницу 18:00 | Следующее напоминание в субботу 18:00 в локальном календаре |
| Повтор «По будням», claim в пятницу 18:00 | Следующее напоминание в понедельник 18:00 |
| Задача выполнена | Архив; nextReminderAt = 0; новые напоминания этой задачи не назначаются |

Автоматический перенос и очередное напоминание сейчас не меняют `updatedAt`. Поэтому сортировка «По дате изменения» не поднимает задачу после каждого уведомления. Явная правка текста, расписания и выполнение меняют `updatedAt`.

### 12.4. Часовой пояс и DST

В модели нет сохранённого часового пояса задачи: моменты хранятся как epoch milliseconds. Форматирование, ввод и календарные повторы используют текущий системный `TimeZone`, передаваемый Core. При поездке в другой пояс тот же сохранённый момент отображается другим локальным временем. Не обещать «всегда в 09:00 по домашнему времени» и не рисовать несуществующий переключатель timezone на задаче.

Добавление часа/10/30/60 минут — прошедшее физическое время. Добавление календарного дня, недели и поиск буднего/выходного дня выполняются через календарные операции `kotlinx.datetime` с timezone; такой интервал при переводе часов может длиться не ровно 24/168 часов. UI не пересчитывает дни вручную как `24 * 60 * 60 * 1000`.

`TaskSchedule.parse()` сейчас использует `LocalDateTime.toInstant(zone)` внутри `runCatching`. В коде нет отдельного продуктового разрешения неоднозначного локального времени при обратном переводе часов или отсутствующего времени при прямом переводе. Публичный контракт библиотеки выбирает более ранний момент при двойном времени; при пропуске времени использует смещение до перехода, из-за чего обратное отображение может дать более позднее локальное время. Это правило проверено по [официальному описанию toInstant](https://kotlinlang.org/api/kotlinx-datetime/kotlinx-datetime/kotlinx.datetime/to-instant.html); открытая страница относится к текущему API, а закреплённая в Kasha версия 0.7.1 дополнительно проходит перечисленные ниже runtime-тесты.

Целевая защита: после преобразования ввода выполнить обратное отображение полученного момента в том же timezone. Если показанные пользователю дата/время изменились из-за перехода, до сохранения явно показать фактическое время: «В этот день часы переводятся. Напоминание будет в 03:30» — с действиями «Сохранить на 03:30» и «Изменить время». Не сохранять невидимую нормализацию. Для неоднозначного времени сохраняется правило более раннего момента, а рядом с итогом показывается конкретный UTC-offset и пояснение «Первое наступление этого времени». Второго выбора «первое/второе» в этой версии нет. Проверка неоднозначности/offset относится к общему календарному результату, не к второму независимому календарному алгоритму в iOS/UI.

Проверка даты проводится повторно при сохранении после смены системного пояса, сворачивания или перехода через DST. Разработчик должен подтвердить поведение текущей зависимости `kotlinx.datetime 0.7.1` тестом для выбранных зон и фактическим форматированием. Наличие вызова `toInstant()` не является доказательством полного UX таких границ.

### 12.5. Доставка уведомлений

Общий UX различает: расписание сохранено; ОС разрешила уведомления; адаптер поставил ближайшее уведомление; уведомление фактически показано. Успешное сохранение задачи подтверждает первое, а не все четыре.

| Платформенная основа | Подтверждённое ограничение в прочитанном коде | Как это отражать |
|---|---|---|
| macOS desktop `main` | `DesktopReminder` показывает уведомление через работающий процесс; `available` зависит от macOS | Не обещать напоминание после полного закрытия приложения |
| Web `main` | `claimTaskReminders()` возвращает пустой список; полноценный системный scheduler не подтверждён | Сообщить «Уведомления в этой версии недоступны» в редакторе/настройках |
| iOS `main` | Базовая композиция без производственного delivery gateway | Не выдавать локально сохранённую задачу за проверенное системное напоминание |
| iOS PR #9 | Одноразовый `UNTimeIntervalNotificationTrigger`; очередь пересоздаётся при sync | Допускается ближайшее системное напоминание после настройки; многократные повторы при длительно закрытом приложении пока не обещать |

При отказе ОС задача сохраняется; рядом с расписанием: «Уведомления выключены в настройках устройства». Действие открытия настроек показывается только при реальной возможности платформы. Не спрашивать системное разрешение заново при каждом редактировании текста; статус доступности должен отделяться от `available = true` адаптера.

При выполнении, изменении срока и удалении системные заявки должны быть обновлены/отменены. В iOS PR при выполнении пересобирается pending-очередь, при удалении дополнительно отменяется доставленная заявка; обработку уже показанного уведомления после выполнения требуется проверить. Нажатие старого уведомления не должно восстанавливать выполненную/удалённую задачу или создавать новую.

## 13. Архив — T04

Вход через «Архив» на экране задач. Заголовок «Архив», дополнительная доступная подпись «Выполненные задачи». Back/команда «К активным» возвращает к прежнему списку и scroll. Нижняя вкладка по-прежнему «Задачи»; отдельного пятого пункта нет.

Строка показывает completed glyph, текст и дату выполнения из `completedAt`. Дата прежнего срока не доминирует и при необходимости доступна в деталях. Completed glyph в архиве — статус, не переключатель обратно в активные. Сортировка доступна теми же четырьмя режимами; «По дате изменения» естественно использует время выполнения, так как Core обновляет `updatedAt` при завершении.

Текст выполненной задачи читается без редактирования. Нет «Выполнить» и «Изменить срок»; показываются «Выполнена …» и доступное «Удалить задачу». Восстановление, дублирование и перезапуск напоминаний не добавляются без общего контракта.

Пустой архив: «Здесь появятся выполненные задачи». Не использовать сообщение активного списка «Пока нет задач», чтобы не возникало впечатление потери всех данных.

## 14. Удаление задачи — T05

Команда в деталях активной или выполненной задачи открывает подтверждение «Удалить задачу?»; текст «Задача и её напоминания будут удалены». Кнопки «Оставить» и «Удалить задачу». Фокус на безопасном действии, Enter не подтверждает удаление неожиданно при открытии диалога. После удаления восстановление из архива не обещается: это фактическое удаление сущности, а не её выполнение.

При подтверждении выполняется одна операция, показывается busy, повторный submit исключён. Успех возвращает в исходную выборку — активные или архив — с сохранённой позицией по ближайшему объекту. Ошибка оставляет задачу доступной; «Не удалось удалить задачу» и повтор.

`BrainData.deleteTask()` сейчас удаляет только сущность задачи; привязанный capture и аудиофайл этот метод не удаляет. Поэтому подтверждение не говорит «Аудиозапись будет удалена», и UI не запускает самостоятельный cleanup файлов. Дальнейший срок хранения/cleanup исходников требует отдельного согласованного правила, а не побочного эффекта красивой кнопки.

Для текущего iOS adapter удаление также отменяет уведомление. На каждой платформе этот lifecycle проверяется отдельно: визуальное исчезновение строки не является подтверждением отменённого уведомления ОС.

## 15. Даты, длинные тексты и локализация

Все пользовательские даты отображаются в выбранном языке приложения и текущем timezone. В списках предпочтительны «Сегодня, 14:32», «Вчера, 09:10», затем «12 сентября»; при другом годе — «12 сентября 2025». В редакторе ручной ввод следует явному формату, а полное значение доступно для проверки. Не угадывать американский/европейский формат по разделителю.

Если timestamp отсутствует/равен 0 в legacy-данных, не показывать 1 января 1970 как реальную дату. Metadata скрывается либо заменяется «Дата не указана» в деталях. Для созданного через UI объекта время должно присутствовать; отсутствие данных не маскируется выдуманным «Сегодня».

Проект с длинным словом, URL или текстом без пробелов не раздвигает layout горизонтально. В списке ellipsis и корректный wrapping; в редакторе полный текст. Клавиатура, selection и системное меню копирования работают с кириллицей, латиницей, комбинируемыми знаками и другими включёнными языками. Обрезку производных заголовков на границе surrogate/grapheme необходимо проверить: пользовательские данные не повреждаются ради лимита превью.

Составная accessible label строки не повторяет один текст трижды. Примеры: «Проект „Работа“, закреплён. Открыть»; «Заметка „План запуска“, изменена сегодня в 14:32, есть аудиозапись»; «Задача „Позвонить“, срок завтра в 15:30, напоминать каждый час». Completion получает отдельное «Выполнить задачу „Позвонить“».

## 17. Проверяемые критерии передачи

- **CNT-01.** Во всех списках и редакторах отсутствует отдельное поле title заметки/задачи; изменение первой непустой строки меняет производное имя после сохранения.
- **CNT-02.** Одна запись сохраняется в одну сущность; два быстрых нажатия, повтор после потери ответа и повтор append не создают дублей или повторного текста.
- **CNT-03.** Append сохраняет прежний body и все прежние источники, добавляет новый блок и source relationship; отмена picker ничего не распределяет.
- **CNT-04.** Новый проект из picker возвращает только к исходному capture; запоздавший ответ не открывает чужой поток.
- **CNT-05.** Доступны четыре сортировки; их переключение переживает перезапуск preferences и сохраняет ручную последовательность.
- **CNT-06.** Закреплённые проекты находятся сверху во всех режимах по общему Core; pin/unpin не стирает manualOrder, drag не меняет pin через границу неявно.
- **CNT-07.** Перестановка сохраняет полный валидный набор ID; cancel и ошибка возвращают подтверждённый порядок; keyboard/screen-reader альтернатива достигает того же результата.
- **CNT-08.** Закреплённые заметки находятся сверху во всех целевых режимах по Core; новый контракт pin-порядка ограничен одним проектом. Сохраняется независимый полный manualOrder каждого проекта; общая `noteSort` не становится скрыто отдельной настройкой на проект.
- **CNT-09.** Ошибка загрузки не отображается как пустой список; ошибка сохранения не стирает ввод, курсор и доступ к повтору.
- **CNT-10.** Back, смена вкладки и закрытие dirty-редактора дают осознанно сохранить/отменить; неожиданный snapshot не заменяет локальный текст.
- **CNT-11.** List rows, иконки и trailing-команды доступны при 200% текста, имеют цели 44+ dp и видимый focus; metadata не является обязательным мелким текстом с недостаточным контрастом.
- **CNT-12.** Открытие аудио из заметки использует один player; запись и playback не идут вместе; отсутствие peaks/файла не заменяется придуманной waveform.
- **CNT-13.** Capture из нескольких предложений создаёт одну задачу; проект не требуется; аудиосвязь сохраняется.
- **CNT-14.** Срок строго будущий на момент сохранения; defaultDue не сбрасывает форму при recomposition; первое напоминание совпадает с dueAt.
- **CNT-15.** Семь повторов означают напоминания о той же задаче; перенос dueAt и nextReminderAt соответствуют фактическому Core и понятны в UI.
- **CNT-16.** Автоматический перенос не происходит только в display-слое; `updatedAt` не меняется от одного напоминания, порядок по изменению остаётся предметно верным.
- **CNT-17.** Выполнение подтверждается только после сохранения правок; ошибка сохранения блокирует complete, ошибка complete не убирает задачу из списка.
- **CNT-18.** Выполненная задача находится в архиве, не редактируется и не имеет работающего «Отменить» без Core-контракта; nextReminderAt обнулён.
- **CNT-19.** Удаление требует подтверждения, возвращает в исходную выборку и не обещает удаления аудио; связанные системные уведомления отменяются согласно capability.
- **CNT-20.** Для DST/смены timezone проверены преобразования текущей библиотеки и показано реально сохраняемое время; невозможное время не нормализуется невидимо.
- **CNT-21.** ОС-отказ в уведомлениях не препятствует сохранению задачи; статус расписания не выдаётся за гарантию доставки, ограничение одноразового iOS-уведомления отражено честно.
- **CNT-22.** Нет случайного FAB, профиля, новых фильтров, неподдерживаемого поиска/удаления заметок, искусственных количеств и карточки вокруг каждого абзаца.

Эти критерии дополняют [общую приёмку](./10-acceptance.md). Функциональные изменения вносятся через [план внедрения](./11-implementation-plan.md); документация не считается доказательством их выполнения.
