# Kasha — каноническое техническое задание

Продуктовая база: 12 сентября 2026. Дизайн уточнён 13 сентября 2026.

Этот документ — основной источник архитектурных и продуктовых требований Kasha. Если README, старые verification-документы или комментарии в коде противоречат этим требованиям, приоритет у `docs/SPEC.md`. Подробный целевой UX и визуальный дизайн определяются [дизайн-ТЗ](design/README.md), составленным по новым указаниям владельца продукта. Оно заменяет прежние визуальные решения и явно отмечает необходимые изменения Core/адаптеров, сохраняя архитектуру, local-first и инварианты данных.

## 1. Продукт

Kasha — local-first приложение для голосовых заметок и задач с ИИ-обработкой.

Основной сценарий:

**Записать голос → транскрибировать → при необходимости привести текст в порядок → сохранить в заметки или задачи.**

На Главной после обработки находятся **две отдельные кнопки**:

- **В заметки**;
- **В задачи**.

Общего промежуточного переключателя `Заметка | Задача` нет и добавлять его не нужно.

## 2. Главный архитектурный принцип

В проекте существует **одно максимально самостоятельное ядро `kashaCore`**.

```text
                         kashaCore
        models · domain · rules · contracts · AI ports
                              │
                       shared Kasha UI
                              │
        ┌──────────┬──────────┼──────────┬──────────┐
      macOS      Windows    Android      iOS       Web
        │            │         │          │          │
      thin         thin      thin       thin       thin
      shell        shell     shell      shell      shell
```

Цель:

- максимум общего кода;
- минимум platform-specific кода;
- возможность отделить Core, подключить небольшой слой конкретной платформы и получить тот же продукт;
- отсутствие дублирования бизнес-логики между платформами.

Правило: **если логика может одинаково работать хотя бы на двух платформах, она должна жить в Core или shared UI, а не в platform shell.**

### В Core находятся

- модели данных;
- бизнес-правила;
- проекты, заметки, задачи и capture-flow;
- сортировки и persistent manual order;
- правила append заметок;
- task lifecycle и календарные правила;
- AI-роли и их контракты;
- privacy-контракты AI;
- проверки результатов AI;
- платформонезависимые state/contracts.

### В Core не находятся

- Compose UI;
- конкретные модели Whisper/Qwen/Gemma и т.п.;
- конкретные провайдеры OpenAI/Anthropic/Gemini и т.п.;
- URL внешних API;
- Keychain/Keystore/Secret Service;
- микрофон, playback, filesystem конкретной ОС;
- упаковка приложения.

Конкретные каталоги моделей и провайдеров принадлежат runtime/platform infrastructure, а не Core.

## 3. Shared UI

Основной интерфейс реализуется один раз на Compose Multiplatform.

Platform shell не должен создавать параллельную реализацию продуктовых экранов без объективной необходимости.

Допустимы только platform-specific адаптации поведения, действительно связанные с платформой: safe areas, системные permissions, lifecycle, системные окна, notifications и аналогичные API.

## 4. Local-first и приватность

Kasha должна полноценно работать локально без аккаунта, пользовательского backend и облачной БД.

По умолчанию AI работает локально.

Допускается **явно подключаемый внешний AI**, если пользователь сам выбрал провайдера и подтвердил передачу соответствующих данных.

Запрещено:

- обязательное облако для основной функциональности;
- облачная пользовательская БД как основной storage;
- незаметная синхронизация заметок/аудио;
- telemetry/analytics SDK, передающие пользовательские данные;
- отправка пользовательских данных внешнему AI без явного consent;
- хранение API-key в Core state, Preferences, обычных файлах или логах.

API-key хранится только в защищённом системном хранилище platform layer.

Для внешнего AI интерфейс обязан явно показывать, какие данные могут покинуть устройство.

Desktop/Web может использовать локальный HTTP на `127.0.0.1` как транспорт внутри устройства. Это не считается удалённым backend.

## 5. Разделы

Основная навигация:

1. Главная;
2. Проекты;
3. Задачи;
4. Настройки.

Глобальный плеер доступен в основных сценариях, если не конфликтует с модальным действием.

## 6. Главная и запись

При запуске:

- инициализация приложения;
- Главная;
- при включённом auto-record и отсутствии незавершённой записи запись может стартовать автоматически после получения разрешения.

Во время записи:

- крупный таймер;
- реальная осциллограмма;
- пауза;
- продолжение;
- завершение;
- навигация не уничтожает запись.

Одновременно записывать и воспроизводить аудио нельзя.

Незавершённая запись должна быть восстанавливаемой после сбоя там, где платформа позволяет это реализовать.

## 7. AI pipeline

В продукте три независимые AI-роли:

1. `SPEECH_TO_TEXT` — аудио → текст;
2. `TEXT` — заголовок и приведение текста в порядок;
3. `ROUTING` — оценка релевантности заметки проектам.

Это **не три Core и не три приложения**. Core остаётся единым; AI-роли — независимые контракты внутри общей архитектуры.

Для каждой роли движок выбирается независимо.

Локальные и внешние реализации должны быть взаимозаменяемыми за одним контрактом.

Core не должен зависеть от названий конкретных моделей/провайдеров.

### Text processing

«Привести в порядок» может:

- исправлять пунктуацию;
- разбивать текст на абзацы;
- убирать случайные повторы;
- нейтрализовать мат согласно текущему продуктовому правилу.

Обязательно сохранять:

- исходные мысли;
- числа;
- имена и названия;
- отрицания;
- фактический смысл.

AI не должен додумывать факты.

Проверки результата должны применяться независимо от того, локальная модель используется или внешний провайдер.

### Routing

Релевантность проекта — отдельное состояние и не должна уничтожать пользовательскую сортировку проектов.

Для внешнего AI предпочтителен один batch-запрос по проектам вместо отдельного сетевого запроса на каждый проект.

## 8. Запись → заметка

На Главной пользователь нажимает **«В заметки»**.

После этого:

1. при необходимости выполняется AI routing;
2. открывается выбор проекта;
3. пользователь выбирает:
   - создать новую заметку;
   - добавить текст в существующую заметку.

При append:

- старый текст не переписывается;
- новый текст добавляется строго в конец;
- аудиоисточник остаётся отдельным source;
- повторное сохранение одного capture не создаёт дубль.

Одна запись не может одновременно стать заметкой и задачей.

### Заголовок заметки

Отдельного поля заголовка нет.

Заголовок — первая непустая строка текста. Это правило едино для всех платформ.

## 9. Запись → задача

На Главной пользователь нажимает **«В задачи»**.

Задача является полноценной, но простой сущностью Kasha.

Поддерживаются:

- текст;
- дата создания;
- дата изменения;
- persistent manual order;
- срок;
- локальное напоминание;
- частота повторного напоминания;
- изменение срока;
- редактирование текста;
- выполнение;
- архив выполненных;
- удаление.

Поддерживаемые интервалы напоминаний:

- 10 минут;
- 30 минут;
- каждый час;
- ежедневно;
- еженедельно;
- по выходным;
- по будням.

Не превращать Tasks в корпоративный task tracker: исполнители, команды, комментарии, сложные статусы и серверный workflow не нужны.

## 10. Проекты

Проект содержит:

- название;
- описание/инструкцию;
- дату создания;
- дату изменения;
- pinned-state;
- pin order;
- manual order.

Проект можно создавать, открывать, редактировать, закреплять, сортировать и переставлять вручную.

Инструкция проекта используется AI routing.

## 11. Сортировки

Для проектов, заметок и активных задач доступны:

1. по алфавиту;
2. по дате создания;
3. по дате изменения;
4. вручную.

Manual order является отдельным persistent состоянием.

Переключение на другую сортировку не уничтожает manual order. После возврата в Manual пользователь видит прежнюю расстановку.

## 12. Ручная перестановка

В Manual:

- long-press;
- drag вверх/вниз;
- порядок сохраняется после завершения drag;
- механизм общий;
- после перезапуска порядок сохраняется.

В остальных режимах drag reorder выключен.

Уточнение целевого UX от 13.09.2026: закреплённые проекты располагаются сверху также в Manual; их порядок задаёт `pinOrder`, остальные следуют сохранённому `manualOrder`. Это требует изменения общего правила текущего Core, а не локальной сортировки в UI. Сохранённая ручная раскладка не уничтожается. Подробности: [сценарии контента](design/05-projects-notes-tasks.md) и [план внедрения](design/11-implementation-plan.md).

## 13. Kasha UI

Единый слой продуктовых компонентов называется **Kasha UI**.

Legacy `Brain UI` запрещён.

Продуктовые экраны не должны напрямую создавать альтернативные базовые Material controls, если для них существует Kasha-компонент.

Material/Compose может использоваться как техническая база, но внешний вид не должен ощущаться типовым Material Design.

## 14. Kasha Icons

Текущий единый набор **Kasha Icons** является каноническим.

Правила:

- использовать только `KashaIcon`/`Glyph` в продуктовом UI;
- не подключать Material Icons, SF Symbols, Lucide, Phosphor и параллельные icon packs;
- геометрия и motion иконок централизованы в Kasha UI;
- короткая функциональная анимация допустима на press/hover/focus/drag;
- не создавать второй набор иконок рядом.

CI должен блокировать возврат сторонних icon packs.

## 15. Типографика

Основной шрифт целевого дизайна — **Geologica Variable**.

Использование:

- UI и display используют одну гарнитуру с документированными настройками реальных осей;
- шкала: body 16/23, от micro 11/15 до hero 46/48;
- полноценная кириллица и все поддерживаемые языки обязательны.

Точные веса, интерлиньяж, оси, исходник/лицензия шрифта, контраст и правила масштабирования: [основы дизайна](design/02-foundations.md). Текущий код ещё использует Commissioner; его замена включает pipeline подготовки шрифтов, а не только `Theme`.

## 16. Темы

### Light

Почти белая, с очень небольшим тёплым жёлто-бумажным смещением.

Ориентир фона: `#F7F5EE`.

### Dark

Почти чёрная, с очень небольшим тёплым коричневым смещением.

Ориентир фона: `#191715`.

Не использовать неон, яркий Material-blue, AI-glow, стеклянные сине-фиолетовые градиенты и визуальный шум.

Сдержанное тёплое освещение процедурного объекта записи допускается по [спецификации графики](design/08-graphics-motion.md); декоративные «AI-градиенты» не допускаются. Новое прямое указание владельца разрешает [макросъёмку гречки](design/assets/README.md) **только на сплеш-экране**. На Главной и всех рабочих экранах используется процедурный фон. Официальные `kasha_logo.svg` и `kasha_logo_solid.svg` сохраняются.

## 18. Аудио

STT получает исходное аудио до ускорения и потерь оптимизации.

После успешной обработки допускается локальная оптимизированная версия.

Настройки:

- mono;
- несколько уровней качества;
- сохранённая скорость по умолчанию 1.5×;
- диапазон 1–2×.

Исходник удаляется только после безопасного завершения обработки/публикации итогового файла. При ошибке должен быть доступен retry/recovery.

## 19. Платформенные границы

Ни одна платформа не является архитектурным центром.

Platform-specific слой содержит только:

- entry point/lifecycle;
- permissions;
- microphone;
- playback;
- local notifications;
- filesystem/DB adapter;
- secure secrets;
- конкретный local AI runtime;
- packaging;
- действительно уникальные API ОС.

Бизнес-логика, state, сортировки, task rules, AI contracts и основной UI flow не копируются по платформам.

## 20. Платформы и критерий готовности

### macOS

Production-ready направление: реальный микрофон, playback, local models, local storage, notifications, self-contained packaging.

### Web

Общий UI работает в браузере. Допустим локальный companion/runtime на устройстве.

### iOS

Тестовый shell с заглушками допустим только как UI/build verification.

Production iOS должен получить настоящие адаптеры:

- микрофон;
- playback;
- persistent local storage;
- notifications;
- local AI/model integration;
- secure secret storage для optional external AI.

### Android

Нужен тонкий installable app shell поверх существующих Core/shared UI targets с platform adapters.

### Windows/Linux

Нужно довести desktop packaging и platform services до устанавливаемых приложений, максимально переиспользуя desktop/shared код.

## 21. AI packages и внешний AI

Выбор модели хранится отдельно для каждой AI-роли.

Каталог конкретных моделей не должен быть частью Core.

Для скачиваемых моделей:

- HTTPS;
- pinned SHA-256;
- временный `.part`;
- проверка hash до публикации;
- атомарная замена там, где возможно;
- понятное состояние download/install/error/remove.

External providers подключаются только через изолированный infrastructure adapter.

Core хранит только безопасные метаданные выбора/consent; секреты находятся в platform secure storage.

## 22. Автоматические проверки

CI обязан проверять как минимум:

1. сборку `kashaCore`;
2. Core tests;
3. shared Compose UI;
4. Android target shared UI;
5. iOS shared framework;
6. runtime tests;
7. desktop tests;
8. production Wasm;
9. browser E2E;
10. architectural Core boundary;
11. Kasha UI boundary;
12. Kasha Icons boundary;
13. local-first/privacy boundary;
14. AI role/privacy tests;
15. model manifest/hash tests;
16. шрифты всех восьми языков.

Новая функциональная ветка не считается готовой к merge, пока обязательный CI красный.

## 23. Минимальный E2E

Обязательно проверять:

1. запуск;
2. начало записи;
3. pause/resume;
4. навигацию во время записи;
5. stop;
6. STT;
7. редактирование;
8. «Привести в порядок»;
9. «В заметки» → проект → новая/существующая заметка;
10. новая запись;
11. «В задачи» → срок/повтор → задача;
12. редактирование задачи;
13. изменение срока;
14. выполнение → архив;
15. удаление;
16. четыре сортировки;
17. manual drag reorder;
18. переключение сортировки и возврат в Manual;
19. перезапуск с сохранением данных;
20. local AI без внешней сети;
21. внешний AI только после explicit consent;
22. отказ/ошибка AI не должны уничтожать исходный пользовательский текст или аудио.

## 24. Definition of Done архитектуры

Архитектура готова, когда:

- `kashaCore` можно физически отделить от приложения;
- Core не содержит UI, ОС, конкретных моделей и конкретных AI-провайдеров;
- один shared UI используется платформами;
- для новой платформы требуется реализовать только небольшой набор platform ports;
- вся общая бизнес-логика переиспользуется без копирования;
- приложение локально полноценно работает без аккаунта и удалённого backend;
- optional external AI не разрушает local-first модель;
- обязательный CI полностью зелёный.

**Цель Kasha: 1 Core + 1 shared UI + минимальные platform shells.**
