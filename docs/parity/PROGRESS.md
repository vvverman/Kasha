## Уточнение владельца: максимально общее Core с API приложения

Core должно предоставлять готовое поведение приложения, а не только модели и набор отдельных правил, из которых каждая оболочка заново собирает продукт. Цель — исправлять общее поведение в одном месте и максимально упростить сопровождение платформ.

Обязательные границы:

1. В Core находится платформонезависимая координация сценариев: запуск и восстановление, запись/плеер и их взаимное исключение, обработка, сохранение, идемпотентность, задачи, порядок, применение настроек, privacy-проверки и защита от устаревших результатов.
2. Публичная граница Core предоставляет команды, запросы/наблюдение за актуальным состоянием и явные результаты операций. Потребители не редактируют доменные коллекции напрямую и не воспроизводят правила по отдельным полям.
3. API здесь означает программный контракт. Не вводить обязательный HTTP-сервер, сеть или сериализацию для вызовов внутри нативного процесса. Уже разрешённый локальный Web transport при необходимости отображает тот же продуктовый контракт и не становится вторым ядром.
4. Core вызывает системные возможности через узкие порты; адаптеры возвращают факты и системные события. Core определяет продуктовые последствия, а не содержит проверки вида «если iOS, сохранить иначе».
5. Kasha UI остаётся одним общим слоем: экраны, компоненты, локализация, навигационное представление, фокус, анимации и адаптивная компоновка. Не переносить Compose и визуальные детали в Core ради процента общего кода. Экран обращается к общему API, а не к собственной платформенной бизнес-логике.
6. Оболочка собирает зависимости, подключает Core и Kasha UI, передаёт системные события. Особенности микрофона, разрешений, файлов, уведомлений, защищённого хранилища и упаковки остаются снаружи. Конкретные AI-провайдеры/модели и общий инфраструктурный код переиспользуются вне Core, как требует SPEC; не дублировать их по ОС и не тащить их в домен.
7. Переиспользовать и уточнять существующие контракты. Не добавлять второй параллельный Core API, универсальный framework, шину событий или плагины без конкретной необходимости. Общие правила не должны копироваться даже при разных технических адаптерах.
8. Критерий: изменение правила заметки/задачи/записи требует одной общей правки и общих тестов, а не шести изменений оболочек. Выпуск обновлённых сборок и платформенные регрессионные проверки при этом остаются необходимыми. Новая ОС требует системных адаптеров и упаковки, но не новой реализации пользовательских сценариев и экранов.

Текущая незакрытая граница: `composeApp/.../StudioState.kt` совмещает Compose-состояние с запуском, восстановлением и сохранением. Общую координацию следует отделять от визуального состояния по существующим контрактам и тестам, а не объявлять разделение завершённым после переноса файлов. Уточнение этого раздела — требование и критерий приёмки, НЕ заявление о выполненном рефакторинге.
